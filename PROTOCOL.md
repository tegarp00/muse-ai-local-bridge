# muse-ai-local-bridge — Protocol Specification (V1)

This document is the **shared syntax** of the project: the precise wire
format between the bridge server (running on the user's machine) and any
client (e.g. Muse at muse.ai). It is written so that anyone can
reimplement either side without reading the server source code.

Normative keywords (MUST, MUST NOT, SHOULD) are used in the RFC 2119 sense.

## 0. Design rationale (read this before "cleaning up" the protocol)

The protocol is **GET-based tool API**, not standard MCP Streamable HTTP.
This is deliberate, not legacy:

- The primary client (Muse at muse.ai) runs in a sandbox whose egress
  proxy **blocks outbound HTTP POST**. MCP Streamable HTTP is POST-only
  client → server, so a pure-MCP bridge would be unreachable from the
  chat it is built for.
- Standard MCP remains on the roadmap for universal clients, but V1
  speaks this GET protocol. Do not "upgrade" it without solving the
  POST-egress constraint first.

## 1. Transport

- Base URL: the public tunnel URL chosen by the user, e.g.
  `https://xxx.trycloudflare.com`. The server itself listens on
  localhost only; the tunnel is the sole ingress.
- All requests are HTTP GET. There is no request body.
- All endpoints require authentication (Section 2), no exceptions.
- **Practical payload limit:** tool arguments travel in the URL query
  string, so very large calls can be dropped by intermediaries. Observed
  in practice: a 22 KB `write_file` call had its connection closed without
  response, while a 7.3 KB call succeeded. Clients SHOULD keep a single call
  under ~7 KB and split large writes into sequential chunks (e.g.
  `write_file` the first chunk, then `edit_file` appends). Servers MUST NOT
  silently truncate arguments — oversized input should fail loudly.

## 2. Authentication

- The client MUST send the token in the `X-Api-Key` header on every
  authenticated request.
- Exception (bootstrap): `GET /` and `GET /skill.md` are public and need no
  token, so a fresh client can learn how to connect from the URL alone.
  They carry no secrets.
- Tokens are 256-bit random strings generated by the server at startup
  (or loaded from `--token-file`).
- The server MUST compare tokens in constant time.
- On missing/invalid token: `401` with the error envelope (Section 4).
- The token MUST NEVER appear in chat transcripts or URLs. It is entered
  via the platform's secure connection card and stored in the client's
  credential vault.

## 3. Endpoints

### 3.1 `GET /skill.md`

Returns the skill document (`text/markdown; charset=utf-8`) that teaches
a client how to use this bridge: tool semantics, approval discipline,
and usage examples. This is the same file as
`skills/muse-ai-local-bridge/SKILL.md` in the repo.

Purpose: zero-install client bootstrapping. The client fetches this
after obtaining the token and configures itself — no zip upload, no
manual skill installation.

### 3.2 `GET /api/tools/list`

Returns the list of tools available in the current server mode.

Response data:

```json
{
  "ok": true,
  "data": {
    "mode": "kerja",
    "project_roots": ["/home/user/projects/tokoku"],
    "tools": [
      {
        "name": "read_file",
        "description": "Read a file inside an allowed root.",
        "parameters": {
          "path": "string (project-relative or absolute, MUST resolve inside an allowed root)"
        }
      }
    ]
  }
}
```

In `baca` (read-only) mode, write tools and `run_command` are omitted
from the list.

### 3.3 `GET /api/tools/call`

Invokes one tool. Query parameters:

- `tool` (string, required): tool name, MUST be on the list from
  `/api/tools/list`.
- `args` (string, required): URL-encoded JSON object of the tool's
  arguments.

Example:

```
GET /api/tools/call?tool=read_file&args=%7B%22path%22%3A%22README.md%22%7D
X-Api-Key: <token>
```

## 4. Envelopes

Success:

```json
{ "ok": true, "data": { "...": "tool-specific payload" } }
```

Error (HTTP status 4xx/5xx):

```json
{ "ok": false, "error": { "code": "PATH_OUTSIDE_ROOT", "message": "human-readable" } }
```

Error codes (V1): `MISSING_TOKEN`, `INVALID_TOKEN`, `UNKNOWN_TOOL`,
`BAD_ARGS`, `PATH_OUTSIDE_ROOT`, `FILE_BLOCKED`, `WRITE_ATOMIC_FAILED`,
`COMMAND_NOT_ALLOWED`, `COMMAND_REJECTED_METACHAR`, `COMMAND_TIMEOUT`,
`MODE_READ_ONLY`, `INTERNAL_ERROR`.

## 5. Path rules (applies to every tool taking a path)

1. The path MUST resolve (after symlink resolution and `..`
   normalization) strictly inside one of the server's allowed roots.
   Anything else → `PATH_OUTSIDE_ROOT`.
2. The permanent blocklist is enforced even inside allowed roots:
   `.env` and variants (except `.env.example` / `.env.sample`),
   `*.key`, `*.pem`, `.ssh/`, `.aws/`, `.gnupg/`. Match → `FILE_BLOCKED`.
3. `list_files` and `search_code` SHOULD respect `.gitignore` by default.
   `read_file` with an explicit path bypasses `.gitignore` (explicit
   path = owner intent) but never the blocklist.

## 6. V1 tool reference

Tool names are **frozen** as of V1 — clients depend on them.

### Read tools (all modes)

| Tool | Args | Notes |
|---|---|---|
| `list_projects` | — | Returns allowed roots (one entry in cwd mode, several in config mode). |
| `list_files` | `path` (dir, default root), `recursive` (bool, default true) | Respects `.gitignore`. |
| `read_file` | `path`, `offset` (1-based, optional), `limit` (optional) | Text files returned as UTF-8. |
| `search_code` | `pattern`, `path` (optional), `file_glob` (optional) | Literal match; respects `.gitignore`. |
| `git_status` | `project` (optional) | Per-file porcelain-style entries. |
| `git_diff` | `project` (optional), `staged` (bool) | Unified diff. |
| `git_log` | `project` (optional), `limit` (default 20) | |

### Write tools (`kerja` mode only)

| Tool | Args | Notes |
|---|---|---|
| `write_file` | `path`, `content` | Atomic (temp + rename). Size-capped (default 1 MB). |
| `edit_file` | `path`, `old_text`, `new_text` | Exact match on `old_text`, written **literally** (no unicode-escape interpretation). One match required; zero or many matches is an error, never a silent partial write. Sequential application only. |
| `apply_patch` | `path`, `patch` (unified diff) | Atomic; applied with fuzz factor 0. |

### Command tool (`kerja` mode only)

`run_command`: `command` (string), `project` (optional), `timeout_s`
(optional, default 600).

Execution semantics (MUST):

1. The command string is checked for shell metacharacters **first**:
   `;`, `&&`, `||`, `|`, `$()`, backticks, `<`, `>`, `*` (outside the
   whitelisted pattern itself). Any hit → `COMMAND_REJECTED_METACHAR`,
   before pattern matching.
2. The remaining string MUST exactly match (or anchor-match) an entry
   in the server's allowlist. No prefix/substring matching.
   Non-matching → `COMMAND_NOT_ALLOWED`.
3. Execution is **without a shell**: argv array spawn, working directory
   locked to the target project root.
4. Default allowlist: `npm run build`, `npm run typecheck`, `git status`,
   `git diff`, `git log`. Extended at startup via `--allow` patterns.
5. On timeout → `COMMAND_TIMEOUT`; partial output is returned in `data`.

## 7. Approval model (honest statement)

Approval is enforced **client-side**: the AI client MUST obtain explicit
owner approval (showing the full command text / file path and diff)
before calling any write tool or `run_command`. The server trusts that
its caller did so. The threat model covers outsiders and mistakes, not
the owner attacking themselves. See `SECURITY.md`.

## 8. Audit

The server appends one line per write-tool call and per `run_command`
to `~/.muse-ai-local-bridge/audit.log`:
`timestamp, tool, path/command, result`. Append-only.

## 9. Versioning

- This spec is V1. Breaking changes require a spec version bump and a
  new `/api` path segment (e.g. `/api/v2/...`); V1 endpoints keep
  working.
- Additive changes (new tools, new optional args, new error codes) do
  not require a version bump.
